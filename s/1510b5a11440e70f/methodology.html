How we test

The whole operation is one test, run carefully and repeated often: a fixed prompt, fixed settings, and a strict path from generation to publication. Everything else is bookkeeping. The code lives in the private laboratory; this page documents behavior, not internals.

Generation

Each candidate starts from the canonical benchmark wording plus an expanded visual specification, with model settings recorded. The wording is Simon Willison's, from October 2024 — the man behind this entire situation. The first batch is 8–12 independent samples from the same prompt and settings.

Deterministic checks

Every candidate is checked programmatically: well-formed XML with a valid SVG root, no scripts or external requests, no embedded rasters or external fonts, sane file size and element counts, a usable viewBox, clean renders at 256×256, 1024×1024 and transparent, and reproducible hashes of everything.

Critique

Candidates are scored on separate axes — prompt compliance, pelican anatomy, bicycle mechanics, bird–bicycle interaction, composition, editability, and a few more — with written defects, never a single unexplained number. The beak is always the hardest part.

Repair

Failed details (a beak, a pedal, a wheel) get localized edits with the same toolchain. Each repair is a new candidate with a parent pointer, forming a family tree of increasingly confident pelicans. Maximum three repair rounds per finalist: we believe in second chances, not fourth ones.

Publication

Nothing enters this site without passing the publication checklist and a secret scan. Provenance for every asset is documented in provenance.md.
